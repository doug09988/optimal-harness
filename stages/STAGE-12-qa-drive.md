serialization, and execution mechanics; the model supplies judgment and content
as plain text.

## The change — QA becomes a driven sequence

1. **Test-plan call:** one constrained call. The model replies with the list of
   acceptance test names it intends to write (one per line, plain text). The
   runtime parses non-empty lines as the plan (dedupe, keep order, cap at a
   sane maximum — pick 40). An unparseable/empty plan is a model error (one
   re-ask, then the stage's model-error class).
2. **Per-test calls:** for each planned test name, one call whose prompt
   carries the spec/artifact context that test needs and the contract: "Reply
   with only this test function's Python code. No JSON, no envelope, no other
   tests." The entire response is that function's code (existing code-fence
   stripping may apply). Invalid/empty code for a test = re-ask that test once
   with the reason; a second failure marks that test `unwritable` in the
   report — it does NOT kill the stage.
3. **Assembly + execution by the runtime:** the runtime assembles
   `test_acceptance.py` (imports/header it generates + the accepted test
   functions), writes it through the existing artifact path, and runs it via
   the EXISTING executor mechanism with the existing timeout. Execution
   results (pass/fail per test, output tail) are recorded as board events in
   the existing shapes.
4. **Report call:** one driven call carrying the execution results; the model
   replies with its findings as plain text whose FIRST line is exactly
   `PASS` or `FAIL` (its verdict on the artifact under test). Strict first-line
   parse, one re-ask, then the model-error class.
5. QA's handoff is generated by the existing generated-handoff flow from the
   assembled artifact + execution record + report, as today.

Out of scope: other stages' loops; the executor itself; test criteria (the
model still decides WHAT to test — the runtime owns only mechanics);
budgets; stage-9 policy. QA's existing obligations (acceptance tests derived
from the SPEC alone; the FIXER may not edit them) must be preserved: the
assembled file is written by the runtime from model-supplied test bodies, and
the existing protections on the file after QA completes stay as they are.
