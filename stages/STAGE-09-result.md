# STAGE-09 result — stage-attempt retries

Implemented on the existing `codex/stage-09-stage-retries` worktree. No commits or Git metadata changes were made.

Model-side action-format exhaustion, INTAKE document-format exhaustion, REVIEW section exhaustion, invalid/repeated-action no-progress, and handoff exhaustion now permit two retries (three failed attempts maximum) within the same stage task. Failure recording and requeue/escalation are one fenced SQLite transaction. Each retry is claimed as a fresh generation, with fresh runtime state, its own brief, manifest, evidence, handoff, checkpoints, and usage row. The brief retains ordered `attempt_failures`, including generation, exact reason, and the last bounded denial/tool/template context. Terminal escalation retains all attempt reasons in its audit event.

The allowlist excludes budget breakers, verifier/check defects, pinned-input and checkpoint integrity errors, missing-deliverable errors, obligation errors, transport errors, and honest worker failures. Gate and FIXER-cycle code is unchanged. A model-side failure inside a FIXER task has the same bounded retry behavior; it does not increment the defect cycle. Existing outputs persist, but a retry must validate and checkpoint its deliverables again. Identical valid INTAKE output from a prior attempt can now be checkpointed in the new generation.

Budget semantics: the existing stage-task call, fresh-token and wall-clock envelopes are SHARED across all generations, including lease reclaims; they are not per-attempt. The runtime ledger starts from durable cumulative usage, and the board independently enforces cumulative usage. Wall time runs from the first claim and includes time between attempts. Exhausting an envelope prevents requeue; exhausting the remaining envelope during a retry prevents further dispatch. Prompt, observation, completion and command limits retain their existing meanings. FIXER-cycle budgets remain unchanged. This repository has no separate configurable project-wide aggregate budget; sharing the original stage-task envelopes avoids increasing the project's existing stage-budget allocation. No new budget or cap multiplier is introduced. Manifests declare the budget scope, and meter responses expose stage totals alongside generation usage.

Board task listings report `attempts` (claimed generation count) and ordered failure history. Project listings, including the existing CLI/result writer, report `stage_attempts` per task, stage and cycle, distinguishing the separate REVIEW occurrences and FIXER cycles. Successful and failed finish events include generation; historical failure handoffs/manifests remain intact.
